# 指南：实体系统与局内对象管理

> 本文回答两个问题：
> 1. 框架删掉了 Entity 接口族后，**局内对象（单位、子弹、道具等）该怎么管理**？
> 2. **什么时候才真正需要一套"正式实体系统"**？该选 GameObject 组件式还是 ECS？

---

## 一、背景：删掉了什么，为什么删

`Maple.Core` 早期有一族空接口：`IEntity` / `IHasId` / `IIdAllocator` / `IEntityFactory` / `IEntityLifecycle` / `IEntityUpdater` / `IEntityInitializer` / `IContextApplier` / `ISystemOrder` 和 `EEntityCreateFailReason`。

它们想搭一套通用「实体管理脚手架」：Id 分配 → 工厂创建 → 生命周期回调 → 逐实体 Update → 有序系统。但**从未有任何实现、任何使用**，只是"承诺了但没兑现"，还在总纲里造成"框架好像有 Entity 系统"的误导。

按 YAGNI 原则，收束阶段将其**全部移除**。这不是否定实体系统的价值，而是：**没想清楚需求就先立一堆接口，是负债不是资产**。将来真需要，按那时的真实需求重新设计，比留一套空壳强。

---

## 二、没有实体系统，怎么管理局内对象？（本项目就是范例）

BattleAgent 这个战棋游戏**从头到尾没用任何实体接口**，对象管理干净利落。它用的就是绝大多数中小项目的正解：**普通数据类 + 一个 Manager 持有集合 + 逻辑与表现分离**。

### 2.1 三个角色

| 角色 | 本项目对应 | 职责 |
|------|-----------|------|
| **数据类**（纯 C#） | `UnitData` | 一个局内对象的运行时状态（血量、位置、冷却…），可变 |
| **集合持有者 / Manager** | `MatchState`（持 `List<UnitData>`） | 拥有所有对象，负责增删查 |
| **驱动者** | `MatchController` | 推进回合、执行指令、改数据、发事件 |
| **表现层**（可选，分离） | `UnitView` / `MatchView` | 只负责显示，订阅数据变化，不含逻辑 |

### 2.2 关键点逐条

- **数据用普通类，不继承任何框架接口**。`UnitData` 就是个 `class`，构造时从配置（`UnitStats`）拷入不变量，运行时字段可变。没有 `IEntity` 也活得很好。
- **Id 用简单自增**。`MatchController` / `GameBootstrap` 里 `int id = 0; ... new UnitData(id++, ...)`。不需要 `IIdAllocator`——一行 `id++` 就是 Id 分配器。
- **集合就是 `List` 或 `Dictionary`**。少量对象用 `List` 遍历；需要按 Id 频繁查就用 `Dictionary<int, UnitData>`。不需要 `IEntityFactory` / `EntityManager`。
- **生命周期靠 Manager 的方法**，不靠 `IEntityLifecycle`。创建=加进集合，销毁=移出集合（+ 通知表现层销毁 View）。
- **"Update"靠 Manager 统一驱动**。回合制根本不需要逐帧 Update；实时制也是 Manager 在一个 `Tick` 里遍历集合处理，而不是每个对象各自 `Update`（呼应框架"统一 Tick、少用散落 Update"的取向）。
- **逻辑与表现分离**。`UnitData`（逻辑）和 `UnitView`（表现）分开，View 订阅数据/事件刷新。这条比"要不要实体系统"重要得多。

### 2.3 一个可复用的最小 Manager 模式（够用就好）

真需要"通用一点"的容器，几十行足矣，不必上框架级接口：

```csharp
public sealed class ObjectRegistry<T>
{
    private readonly Dictionary<int, T> _items = new();
    private int _nextId = 1;

    public int Add(T item)
    {
        int id = _nextId++;
        _items[id] = item;
        return id;
    }

    public bool TryGet(int id, out T item) => _items.TryGetValue(id, out item);
    public bool Remove(int id) => _items.Remove(id);
    public IReadOnlyCollection<T> All => _items.Values;
    public void Clear() => _items.Clear();
}
```

这已经覆盖了原来那堆 `IIdAllocator` + `IEntityFactory` + `EntityManager` 想做的 80%，且没有任何抽象负担。**需要再抽象，不要提前抽象。**

## 三、什么时候才真正需要"正式实体系统"？

出现下面**多个**信号时，"数据类 + Manager"开始吃力，才考虑上正式系统：

1. **对象种类多、且共享大量统一机制**：统一 Id、统一生命周期、统一池化、统一序列化/存档、统一网络同步——每种对象都手写一遍样板，重复到痛。
2. **横切系统爆炸**：移动系统、碰撞系统、AI 系统、渲染同步系统…每个都要"遍历所有相关对象"。当"系统 × 对象"的组合变多，按类型手写遍历变乱——这正是 ECS 的核心动机。
3. **性能压力**：成百上千甚至上万活动对象，需要 cache 友好、数据连续、可并行——面向对象的散落引用扛不住。
4. **需要通用能力**：基于统一实体表做存档/回放/快照/回滚/帧同步。

反过来：**回合制、策略、卡牌、解谜、对象数量在几十到几百这一量级**——几乎永远用"数据类 + Manager"就够，上实体系统是自找复杂。

## 四、若要做正式系统：GameObject 组件式 vs 纯数据 ECS

| 维度 | GameObject + 组件（MonoBehaviour） | 纯数据 ECS（DOTS 或轻量自研） |
|------|-----------------------------------|-------------------------------|
| 上手 / 心智 | 低，贴合 Unity，Inspector 可视化 | 高，思路转向数据导向，调试更难 |
| 表现与逻辑 | 易耦合（组件里既有数据又有 MonoBehaviour） | 天然分离（数据是数据，系统是系统） |
| 性能 / 规模 | 大量实体时 GC、遍历、Update 开销大 | 强，cache 友好、可 Job 化并行 |
| 与 Unity 生态 | 无缝（物理、动画、UI 组件直接用） | 割裂（需要 hybrid / 转换层） |
| 适合 | 对象不多、强依赖 Unity 组件、快速迭代 | 海量实体、极致性能、数据导向玩法 |

**决策指引**：

- 中小体量、强 Unity 组件依赖（技能挂物理/动画/特效）、迭代速度优先 → **GameObject 组件式**。
- 海量同质实体、需要极致性能与并行（弹幕、大规模兵团、模拟） → **ECS**。
- 介于两者、只是想要"统一管理" → 先回到第二节的 **"数据类 + Manager"**，别急着上 ECS。

---

## 五、和 MapleFramework 的关系（避免重蹈覆辙）

- 框架 **Core 层不预设实体系统**。局内对象管理是**游戏规则**，属于游戏层，框架不越界（呼应总纲"框架不含游戏规则"）。
- 将来某个项目真做出了成熟、可复用的实体/ECS 层，且**多个项目都要**，再考虑把**稳定后的**通用部分抽成一个**独立扩展模块**（类似 `Maple.Extensions.*`），而不是先在 Core 立空接口。
- 一句话纪律：**先在游戏层跑通、被多个项目验证，再上升为框架接口**。这正是当初空接口的教训。
